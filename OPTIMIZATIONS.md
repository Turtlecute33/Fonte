### FONTE-OPT-01: Wait for the list read before the settings collector reschedules the update job
- **What**: The settings collector at FonteApp.kt:103-105 starts on Main.immediate inside onCreate, before the IO coroutine reads apps.json. Its first value is the in-memory default Settings(), and drop(1) drops it. The loaded settings then count as a change, so UpdateJob.schedule(replace = true) runs at each cold start. This occurs for each install that stores non-default settings: all upgrades from 0.1.0-0.1.4 (they stored "unmeteredOnly": false), and all users who changed the interval or auto-install. Effect 1: each cold start (app open, install-result broadcast, DownloadJob) moves the next check to now + period. Effect 2: when UpdateJob itself starts the process, JobScheduler.schedule replaces job ID 1 and stops the running job. The background check and the silent installs then do not complete, and the new job waits a full period.
- **Where**: app/src/main/kotlin/app/fonte/FonteApp.kt:103-105 (FonteApp.onCreate, settings collector); app/src/main/kotlin/app/fonte/work/UpdateJob.kt:40-56 (UpdateJob.schedule); app/src/main/kotlin/app/fonte/data/Store.kt:31,40,43-65 (Store._state, awaitLoaded, load)
- **Change**: Make store.awaitLoaded() the first statement of the coroutine at FonteApp.kt:103. Keep all other lines. Line 101 (replace = false, with the fe9b34d migration of old unmetered jobs) continues to do the start-up scheduling.
- **Benefit**: Background checks and silent installs run to the end again when the job starts a cold process. App opens and broadcasts no longer push the next check back by a full period. This applies to upgraded installs and to all non-default settings. The owner phone went 0.1.4 -> 0.1.5 -> 0.1.6 (NEXT-STEPS sections 1 and 2.0), so it is probably affected.
- **Evidence**: FonteApp.kt:49 scope = SupervisorJob + Dispatchers.Main.immediate, so the launch at :103 runs at once on the main thread. The load runs later on IO (:88-89). Store.kt:31 _state = MutableStateFlow(Data()), so the first collected value is the default. Store.load sets the loaded Data (Store.kt:46-65). Defaults: Models.kt:78-84. At 6617f28 (0.1.4) the unmeteredOnly default was false, and Store.encode always writes the settings. 6c2db46 keeps a stored value. UpdateJob.kt:46 returns early only when replace is false. AOSP JobSchedulerService cancels and stops a running job with the same ID when the app schedules it again. The collector is the only replace = true caller. Not reproduced on a device.
- **Safety**: Lines 103-105 come from 451559c (git blame), not from a 'Report:' commit. UpdateJob.schedule and its fe9b34d migration (FONTE-PERF-004) do not change. No stored data, preference key, job ID or JobInfo changes. No dependency.
- **Verify**: On an emulator, put "unmeteredOnly": false in apps.json of a debug build, run am kill, then cmd jobscheduler run -f app.fonte.debug 1 (the debug build has applicationIdSuffix ".debug", app/build.gradle.kts:42). Without the fix, no FonteLibrary 'Check' lines come and dumpsys jobscheduler shows a new window. With the fix, the check lines come and the window does not move.
- **Effort**: S. **Risk**: low. **Net lines**: about +1 (estimate).
- **Verified**: JAVA_HOME=/opt/homebrew/opt/openjdk@21 ./gradlew :app:testDebugUnitTest :app:assembleDebug passed (52 tests, 0 failures); javap shows the awaitLoaded call in the collector coroutine. Not checked: the emulator test in Verify and no run-time check on a device (no emulator or device was used).

### FONTE-OPT-09: Delete leftover APKs before the list read
- **What**: installer.cleanUp() deletes all files in cache/apk and cache/index. It runs last in the start-up IO coroutine, after load, addSelf, packages.refresh (2 binder calls per tracked app) and notifier.setUp. When the system runs a user DownloadJob again in a new process after a process death, the job waits only for awaitLoaded. It can then create the APK file (Http.kt:98) before cleanUp runs. cleanUp then unlinks the file, getPackageArchiveInfo returns null, and the user sees 'Not a valid signed APK', which looks like a security refusal.
- **Where**: app/src/main/kotlin/app/fonte/FonteApp.kt:88-100 (FonteApp.onCreate); app/src/main/kotlin/app/fonte/install/Installer.kt:395-398 (cleanUp); app/src/main/kotlin/app/fonte/work/DownloadJob.kt:39-42; app/src/main/kotlin/app/fonte/net/Http.kt:98
- **Change**: Move installer.cleanUp() from FonteApp.kt:100 to the first line of the IO coroutine, before store.load(). All install entry points wait for the load (DownloadJob and runBackground through awaitLoaded, the UI through ready), so no APK file can exist before the cleanup ends.
- **Benefit**: A user download that the system runs again after a process death does not fail with a false 'Not a valid signed APK'. The risk is highest with many tracked apps, because the package reads then take longer.
- **Evidence**: Order today: FonteApp.kt:89 load, :90 addSelf, :92 packages.refresh, :99 setUp, :100 cleanUp. DownloadJob.kt:40-41 waits only for awaitLoaded, then needed() and install. Http.download opens the file with CREATE before the request (Http.kt:98). Installer.read uses the file path (Installer.kt:252-255). Race found in the code; not reproduced.
- **Safety**: FonteApp.kt:100 comes from 451559c. cleanUp last changed in 778b9a4 (0.1.1, before the audit). The cbfcf35 (Report) lines 91-98 do not change. The same files are deleted at the same process start. No storage format, check or dependency changes.
- **Verify**: The splash now also waits for the listing and deletion of two cache folders (usually empty). This is a zero-cost reorder. The owner can skip it if only proven wins are wanted.
- **Effort**: S. **Risk**: low. **Net lines**: about 0 (estimate).
- **Status**: approved

### FONTE-OPT-10: Treat a stack overflow from the JSON parser as an unreadable answer, not a crash
- **What**: Platform org.json parses nested arrays and objects by recursion and has no depth limit. A body of about 100k '[' (far below MAX_BODY 8 MB and MAX_IMPORT 16 MB) overflows the stack of a Dispatchers.IO thread. StackOverflowError is an Error, so the catch (e: Exception) blocks do not catch it. In Library.check it escapes through checkAll to the app-scope launch, which has no handler, and the process crashes. Only a self-hosted GitLab or Forgejo host can send such a body. When such an entry is in the list (for example from an imported export, with checkedAt 0), each app open and each background run crashes until the user removes the entry. ## Areas in good shape

- Cold start: no disk, network, Keystore or JNI work on the main thread. The HttpEngine and the Keystore key are lazy, and the APK has a baseline profile. The measured cold start is 478-494 ms (NEXT-STEPS 2.0). GrapheneOS exec spawn takes most of this time.
- Background: one periodic JobScheduler job, and user downloads run as user-initiated data-transfer jobs. There are no wake locks, alarms, foreground services or polling loops.
- Network: one shared HttpEngine, ETag/304 on all sources, a limit on parallel checks and downloads, a 30 s timeout, a stall watchdog and a GitHub rate-limit back-off.
- Hot paths: the list is built and sorted off the main thread (PERF-008), progress and notifications are throttled, store writes are coalesced, Home items have key and contentType, and icons are drawn off the main thread.
- Storage: AtomicFile writes, coalesced saves under a Mutex, a damaged apps.json is kept aside, and receivers and jobs wait for awaitLoaded().
- Install pipeline: CancellationException is rethrown, a late cancel does not clear a committed session, a failed commit abandons its session, and the self-install runs last.
- Lifecycle: collectAsStateWithLifecycle, install prompts collected with repeatOnLifecycle(STARTED), jobFinished in finally, and no long-lived object holds an Activity or a View.
- Shrinking: R8 full mode and resource shrinking are on, there is no third-party library and no native code, and the app code is 160 KB of the 2.16 MB dex. Compose and material3 make up most of the remaining size, and they are the chosen UI stack.
- Abstractions: no DI and no forwarding layers. Each interface has a reason (test fake, 4 source implementations, pure Gate).
- UI: predictive back, shared motion from motionScheme, clear progress and error feedback, empty and first-run states, accessibility actions from the review, and confirmations before destructive actions.
